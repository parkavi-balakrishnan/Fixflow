# FixFlow Project Details and Handover

This document describes the current implementation for the next developer. It is based on the source and data in this checkout. It does not imply that all retrieved scenarios or links have been judged semantically correct.

## 1. Purpose and boundaries

FixFlow is a prototype that converts Samsung troubleshooting queries into structured plans grounded in a small supplied set of SIIS records. It has a FastAPI adapter, in-memory semantic cache, hybrid SIIS retriever, deterministic SIIS parser, separate deeplink catalog matcher, response validation, and a local variation benchmark.

There is no generative model call, neural embedding model, hosted vector store, database-backed cache, online adaptation, or dynamically authored troubleshooting advice. The “AI/ML” techniques actually used are scikit-learn TF-IDF vectorization and cosine similarity, local Okapi BM25 lexical ranking, NumPy scoring, and deterministic hand-authored rules and synonym expansions.

## 3. Input data and derived data

- `data/siis_responses.json` contains 20 raw canonical scenario records. Each has an `original_query` and a SIIS title/content payload. The raw content is the source of troubleshooting text; it does not itself carry attached deeplink objects.
- `data/deeplinks.json` is a separate catalog (578 records in the validator's catalog description). Entries carry masked `bixby://` URIs plus metadata such as message, description, type, and sometimes a validation object. The masked URI is an identifier and is not a feature used for semantic matching.
- `data/processed_knowledge/processed_siis.json` is generated by `KnowledgeStore`/`SIISPreprocessor` from raw SIIS. It stores extracted metadata and searchable text. A raw-file mtime newer than the processed file triggers rebuild.
- `data/sample_output.json` is an illustrative response artifact. It is not the canonical output for every input.
- `data/input.txt` and `data/schema.py` are repository artifacts; the running pipeline schema is `src/schema.py`.

## 4. Query normalization and pipeline execution

`FixFlowPipeline.troubleshoot(query, siis_response=None, device=None, model=None)` executes in this order:

1. **Normalize and cache lookup.** `SemanticCache` normalizes punctuation/spacing and maps forms such as `flip 7` to `flip7`. The pipeline's prewarm variation builder separately strips list numbering and creates scenario signatures. Exact cache identity is distinct from L2 similarity.
2. **L1 exact cache.** A normalized-key dictionary lookup returns the stored structured response on exact match. This behavior remains independent of the semantic guard; see the cache insertion issue below for validation caveats.
3. **L2 semantic cache.** The cache vectorizes stored query phrases and the current query with word-level TF-IDF (unigrams, English stop-word removal, sublinear term frequency), then computes cosine similarity. The best score must meet `FIXFLOW_CACHE_THRESHOLD` (default `0.30`) and pass compatibility checks before returning a hit. Accepted L2 results are promoted into L1. A rejected candidate is a miss and falls through to retrieval.
4. **Retrieval.** When the caller did not supply an explicit `siis_response`, `SIISRetriever` searches the canonical SIIS records through the preprocessed `KnowledgeStore`. If a caller supplies `siis_response`, that payload is extracted instead of selecting a scenario.
5. **Extraction and links.** `SIISExtractor` builds the goal/title from the SIIS title, splits heading-based content into up to four sections, forms action names and step groups, classifies action category, and calls `DeeplinkMatcher` for automatic actions. Steps are drawn from SIIS text, with URL stripping and formatting rules applied.
6. **Ordering.** Actions are ordered auto, manual, critical; `ordering.py` also promotes detected disruptive actions to critical. This is deterministic rule-based ordering.
7. **Validation and cache update.** `ResponseValidator` checks schema and rules. If validation fails, the pipeline returns the raw extracted response; the current normal miss path still calls `cache.put` on that response. Canonical prewarming differs: it only inserts responses that passed validation. Pipeline telemetry reports whether cache/retrieval supplied the result, elapsed time, and retrieval details on a miss. The API exposes selected telemetry and gate results as headers.

The cache is in-memory and process-local. Restarting the process clears learned query/response entries; the canonical prewarm happens again if enabled.

## 5. Semantic cache details

### L1 and L2

`SemanticCache` preserves exact normalized lookup as L1. L2 uses TF-IDF cosine similarity across cached query keys/aliases. The threshold is passed to the cache at pipeline construction from `DEFAULT_CACHE_THRESHOLD`, which reads `FIXFLOW_CACHE_THRESHOLD`.

The pipeline prewarming uses `_build_cache_variations` on canonical SIIS `original_query` values. It keeps model/form-factor anchors, selects distinctive source terms using their frequency over the SIIS corpus, and creates a small number of local lexical variants. It does not add all benchmark variations. The runtime guard checks:

- threshold score;
- device/model/form-factor consistency, including conflicting explicit device identity;
- distinct symptom-family agreement;
- meaningful query/candidate token overlap;
- distinction between display size and text size.

This guard intentionally converts weak nearest-neighbor candidates into misses. It is a deterministic heuristic, not a calibrated classifier. It can reject legitimate paraphrases or accept a misleadingly overlapping query; tests should cover both error directions.

## 6. Retrieval and RAG

### Corpus representation

`SIISPreprocessor` extracts device categories from content headers, detects supported device families/models with regexes, extracts selected symptom patterns, parses markdown sections, and builds `searchable_text` from scenario metadata and selected action content. `KnowledgeStore` loads this processed file or rebuilds it from the raw 20 records.

`SIISRetriever` searches scenario-oriented text (title, canonical query, device/category/model and symptom metadata, section titles) rather than treating all procedure text as equal scenario evidence. Query text can be expanded with local synonym groups covering families such as touch response, display flicker, display sizing, black screen, and email. Retrieval computes:

- word unigram/bigram TF-IDF cosine scores;
- BM25 lexical scores over the same scenario-oriented index;
- regex-based device affinity;
- deterministic symptom/context reranking based on scenario/query signals, title overlap, model evidence, and selected context checks.

The top candidate supplies the raw SIIS record to extraction. Scores are ranking heuristics, not calibrated relevance probabilities. Current default weights in `SIISRetriever` are semantic `0.50`, BM25 `0.35`, and device `0.15` contribution; the device contribution is conditional on textual relevance.

### SIIS processing limits

Extraction is heading-sensitive, takes no more than four sections, and infers category with keyword rules. The corpus is small, symptoms are regex-limited, and the upstream SIIS records can contain generic or off-topic sections. A correct document ID alone does not guarantee the title, selected steps, or action plan are correct for the query.

## 7. Extraction, actions, and response schema

Schema declarations live in `src/schema.py`:

```text
ContextDeeplinkResponse
└── contexts: Goal[]
    ├── goal, title, score
    └── actions: Action[]
        ├── actionName, description, category
        └── stepGroups: StepGroup[]
            ├── steps: string[]
            ├── actionableDeeplink?: Deeplink
            └── validationDeeplink?: ValidationDeepLink
```

`category` values are:

- `auto`: extractor keyword rules infer a settings/navigation action. This category is sent to the deeplink matcher.
- `manual`: physical, service, or unmatched/non-settings actions. Links are normally left absent.
- `critical`: explicit or detected disruptive action such as restart, reboot, safe mode, or reset. Critical is ordered last. The extractor initially classifies some text with simple keyword checks; ordering can promote disruptive content afterward.

Links belong to `StepGroup`, not directly to `Action`. A `Deeplink` contains the URI, description, message, and optional catalog type/classes. A `ValidationDeepLink` contains its URI and optional key/result/condition/value. Because the catalog has sparse validation records, a valid actionable link does not imply a validation link.

## 8. Deeplink matching

`DeeplinkMatcher` creates one text document per catalog item from message (weighted by repetition), description, and `qna_description`; it TF-IDF vectorizes these documents with unigrams/bigrams and ranks by cosine similarity. It never searches the masked URI string. The extractor queries it with action name and up to two initial steps. The default matching threshold is `0.15`; this is separate from semantic cache threshold.

Above threshold, the matcher returns the catalog item and validation data if that entry has it. Below threshold, it returns a `bixby://dummy_positive` placeholder with a generated explanatory message. The response validator confirms URI membership and that auto actions have an actionable deeplink, but does not determine if the link describes the same operation as the action. Thus a catalog-valid link can still be a semantic mismatch.

## 9. Validation and safety gates

`ResponseValidator` checks:

- parseability as `ContextDeeplinkResponse`;
- goal formatting, title/action description shape, score bounds, nonempty actions/steps and formatting constraints;
- catalog membership of actionable and validation URI values, including the mandated dummy actionable fallback;
- required actionable deeplink for automatic actions;
- external URL/domain/markup leakage, while allowing internal Bixby URIs.

The FastAPI route also runs response validation and URL-leak detection for observability headers. These gates are structural and rule-based. They do not evaluate retrieval relevance, grounding fidelity, troubleshooting safety in context, or action/deeplink semantic agreement.

## 10. Benchmark generation and current results

`QueryVariationGenerator` defines nine curated paraphrases for each of the 20 official SIIS query records. `scripts/generate_results.py` checks that there are 20 records and 8–10 variations each, wraps the 180 strings in `BenchmarkCase`, constructs a fresh `FixFlowPipeline`, runs each query through `troubleshoot`, and overwrites `results.jsonl` and `benchmark_report.md` in the requested output directory. The benchmark does not explicitly prewarm these paraphrases.

`run_benchmark` times the full call with `time.perf_counter`; it reads cache hits from pipeline telemetry. Coverage means at least one context with an action. Schema validity is checked by Pydantic. URL leakage scans the serialized response and ignores allowed Bixby links. Failed calls remain in the sample denominator. It does **not** measure scenario relevance or link correctness.

The current `benchmark_report.md` snapshot is:

| Metric | Current artifact |
| --- | ---: |
| Samples | 180 |
| Cache hit rate | 85.0% |
| Coverage | 100.0% |
| Schema validity | 100.0% |
| URL leakage | 0.0% (0 matches) |
| P50 end-to-end latency | 0.69 ms |
| P95 end-to-end latency | 3.98 ms |

These are the saved report values and may vary on rerun. `benchmark_report.json` is a separate older evaluator artifact with a different schema, timestamp, and metrics; `scripts/generate_results.py` does not refresh it. Treat `benchmark_report.md` and the latest `results.jsonl` from the variation script as the relevant pair for this benchmark.

## 11. Development history and decisions

The chronology below summarizes the implementation work recorded during this handover. It is not reconstructed from Git history.

1. **Core pipeline:** an existing retrieval/extraction/validation pipeline and a 35-test suite were the starting point. The pipeline was retained as the normal path for cache misses.
2. **Variation and benchmark tooling:** deterministic query variation coverage and an end-to-end benchmark were added to measure real pipeline calls, output shape, URL leakage, cache hits, and latency.
3. **Canonical prewarming:** prewarming was made scenario-aware using canonical SIIS wording, anchors, distinctive terms, and local aliases. Benchmark paraphrases are not loaded into cache in bulk, avoiding a benchmark-only shortcut.
4. **Cache correctness guard:** after broad semantic hits returned unrelated cached goals, L2 acceptance gained compatibility checks. L1 exact matching stayed unchanged; weak L2 matches now fall through to retrieval even at the cost of hit rate.
5. **Retrieval improvements:** the retrieval path was adjusted to use scenario-oriented evidence, symptom synonym expansion, and signal-based reranking so generic procedural words have less influence. These remain heuristics and do not make the 20-record corpus a robust general support system.
6. **Deeplink flow integration/audit:** deeplinks were traced from the separate catalog through action extraction into each step group's optional fields. The catalog matcher is called for automatic actions; auditing showed that structurally valid nearest-neighbor links can still be unrelated to their actions.
7. **Validation and current state:** schema, catalog URI, formatting, and URL gates are in place. Current 180-case report has full structural coverage and no detected URL leakage, but its metrics do not establish semantic correctness.

## 12. Known issues / follow-up work

These are documented findings; no source-code fixes were made as part of this documentation task.

1. **Deeplink semantic mismatches:** matching is one TF-IDF nearest neighbor with a low `0.15` threshold. A valid link can be semantically unrelated to its action. The validator checks catalog membership, not semantic entailment. Improve action-to-catalog compatibility, calibrate rejection, and create a labeled link evaluation.
2. **SIIS source alignment:** some raw scenario titles/content and canonical query descriptions are inconsistent or broad. Extraction derives goal/title from the selected record title, so source mismatch propagates into response wording and instructions. Curate/verify each record and preserve provenance.
3. **Retriever evaluation gap:** current benchmark measures cache, structure, leakage, and runtime, not correct scenario retrieval. Add expected-scenario relevance metrics and adversarial/near-neighbor evaluations without using the benchmark strings as implementation special cases.
4. **Cache heuristic limits:** compatibility rules and synonym expansion are hand-built; maintain regression cases for both false hits and false misses. Report the best L2 score and rejection reason for diagnosability if telemetry requirements permit.
5. **Category classification:** extractor uses substring/keyword rules and can mistake a phrase such as “turn on” in physical troubleshooting instructions for an automatic action. Improve action classification and ensure risky operations remain critical.
6. **Retrieval configuration mismatch:** `src/config.py` defines `FIXFLOW_SEMANTIC_WEIGHT`, `FIXFLOW_BM25_WEIGHT`, and `FIXFLOW_DEVICE_WEIGHT`, but `FixFlowPipeline` constructs `SIISRetriever(data_dir=data_dir)` without passing those configured values. The retriever therefore uses its constructor defaults (0.50/0.35/0.15), rather than the config defaults (0.40/0.35/0.25). Environment variables are read at module import time; `src/config.py` does not itself load a `.env` file.
7. **Benchmark artifact drift:** `benchmark_report.json` is an older evaluator artifact with different metrics and is not rewritten by `scripts/generate_results.py`. Clarify artifact naming/provenance before submission, but do not delete it until its intended use is established.
8. **Tiny data scale:** only 20 official scenarios and 180 curated variations are in the current benchmark. Results should not be generalized to arbitrary Samsung support queries.
9. **No semantic quality gate:** schema validity, URI membership, coverage, and URL checks do not prove advice is safe, grounded, or relevant. Manual checks found slow touchscreen queries returning “Access Your Galaxy Troubleshooting,” tiny-display queries returning “Blank Or Black Troubleshooting,” and Gmail/display-flicker queries returning “Email Server Not Troubleshooting.”
10. **Invalid miss responses enter cache:** `FixFlowPipeline.troubleshoot` caches the raw response after a failed validation result. A later exact/semantic cache hit may therefore replay a structurally or rule-invalid response. Restrict cache insertion to validated responses and define a safe fallback before relying on cache contents.
11. **Evaluator API drift:** `src/engine/evaluator.py` imports `FixFlowBenchmark` and `load_canonical_scenarios` from `src/engine/benchmark.py`, but neither symbol is defined there. Importing the evaluator will fail until its integration is updated or the old API is restored. The current variation benchmark does not depend on this module.

## 13. Suggested continuation plan

1. Establish a human-reviewed evaluation set containing expected scenario identity, acceptable action intent, and acceptable deeplink intent; keep it distinct from code-level special cases.
2. Fix raw SIIS source inconsistencies at the data/provenance level with review records, then regenerate processed knowledge.
3. Add tests for cache false positives/false negatives, retrieval near neighbors, extraction category errors, and deeplink rejection behavior.
4. Improve and calibrate action/link matching against labels; reject uncertain matches instead of rewarding catalog presence alone.
5. Wire or remove the retrieval weight configuration so environment options behave as advertised; document all effective defaults.
6. Update benchmark reporting to include relevance and semantic link metrics alongside existing structural/latency metrics, with artifact timestamp and configuration.
7. Run the complete test suite and regenerate reports after behavior changes; inspect per-query result rows, not only aggregate hit rate.

## 14. Local setup and useful commands

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn src.api:app --reload
```

Generate the 180-case variation results from the repository root:

```bash
python scripts/generate_results.py --output-dir .
```

Inspect aggregate output in `benchmark_report.md` and per-query rows in `results.jsonl`. The API routes are `GET /health` and `POST /v1/troubleshoot`; the POST body requires a `query` and optionally accepts `device`, `model`, or a supplied `siis_response` title/content pair.
